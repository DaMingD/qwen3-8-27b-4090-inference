# 优化方案说明

本次提交使用：**{{final_config}}**。

## 思路

官方基线是一份能跑通的通用配置。我们没有直接试参数，而是先写一个能解释官方数据、也能被新数据否定的成本模型，用它定位瓶颈，再逐项检验。每个结论都对应一条可测量的证据，结果不符就如实写。

```text
c 个请求一轮的总时长 = c × T_p + 511 × t(c)
T_p：8192 token 的 prefill 耗时     t(c)：每步解码耗时
```

这个模型说明不存在单点优化：低并发主要花在解码上，高并发主要花在 prefill 和调度上（模型推算，prefill 占比并发 1 约 18%，放开并发上限后的并发 8 约 60%，CUTLASS 把后者降到约 45%）。

模型只用 3 个参数，都取自官方表：T_p ≈ 3.46 秒（并发 1 的 TTFT），t(c) ≈ 30.6 + 0.79c 毫秒（TPOT）。按步模拟官方配置（预算 2048、`max-num-seqs=4`），测量方式和请求数与官方相同，运行 `python3 工具/step_sim.py` 可复现：

| 并发 | 请求数 | 时长 模拟/官方 | TPOT P95 模拟/官方 | 端到端 P95 模拟/官方 | TTFT P95 模拟/官方 | TTFT 误差 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 12 | 234 / 234 s | 31.4 / 31.4 ms | 19.5 / 19.5 s | 3.46 / 3.48 s | -1% |
| 2 | 24 | 278 / 286 s | 38.3 / 37.9 ms | 23.2 / 23.8 s | 4.09 / 5.02 s | -19% |
| 3 | 24 | 215 / 220 s | 45.5 / 45.0 ms | 29.7 / 28.9 s | 7.03 / 7.50 s | -6% |
| 4 | 32 | 245 / 249 s | 52.7 / 52.0 ms | 35.4 / 34.9 s | 9.07 / 9.39 s | -3% |
| 8 | 24 | 184 / 187 s | 52.7 / 53.1 ms | 67.3 / 67.4 s | 40.98 / 41.82 s | -2% |
| 2（复测） | 100 | 1159 / 1191 s | 38.3 / 37.9 ms | 23.2 / 23.8 s | 4.09 / 4.61 s | -11% |

时长、TPOT 和端到端的误差都不超过 3%。这是样本内解释：T_p 和 t(c) 既用来定参数又参与比较，吻合不能证明机制正确。并发 2 及以上的 TTFT 没有参与定参数，模型在这一列都偏低，并发 2 最多。模型是否可信，要看下面在拿到数据之前写下的预测。

## 优化路线和结果

| 路线 | 针对的瓶颈 | 做法 | 结果 |
|---|---|---|---|
| 调度：放开并发上限 | 官方 `max-num-seqs=4`，并发 8 时一半请求在排队 | 改为 8，看抢占和 KV 占用 | 并发 8 从 {{base_c8_tps}} 到 {{fallback_c8_tps}} tok/s（{{fallback_c8_gain}}，{{fallback_c8_n}} 个请求），抢占 0，已采用 |
| 调度：减小预算 | 预期混合执行可以共享算力和带宽 | 粗筛 S=2048、512、128 | S=512 +1.5%，S=128 −17.1%，假设被否定，保留 2048 |
| kernel：真实 FP8 | 4090 上官方 FP8 回退到 Marlin，激活仍是 BF16，prefill 没有用到 FP8 的算力 | 三方对比 Marlin、Triton、CUTLASS，自行转换 per-channel 权重 | Triton 淘汰；CUTLASS 配对实验并发 8 再 +26.6%，并发 1 −3.1%，是否采用由质量门槛决定 |
| 投机：MTP | 官方表里唯一没跑通的配置，成本和 248k 词表强相关 | 探针、净收益、死循环复现 | {{mtp_sentence}} |

调度只改变批次组成，不改权重和激活精度。kernel 引入了激活量化误差，所以必须过质量门槛。

## 拿到数据前写下的预测

这些预测在拿到对应数据之前固定，判定规则也提前写好。

| 编号 | 预测 | 判定 | 结果 |
|---|---|---|---|
| P1 | 解码斜率随上下文增长，b ≈ 0.0328 ms/序列/千 token | 未被否定 | 实测 0.0336，差 2.6% |
| P2 | 混合步步长落在相加和取较大值之间 | 没有直接测 | 只看端到端：S=512 在两者之间，S=128 比相加模型低 4.9% |
| P3、P4 | 显存带宽微基准、INT4 解码 | 未测 | |
| P5 | 官方表的 TTFT P95 主要来自窗口开头和小样本 | 方向成立，稳态预测偏低 | 截到官方样本量后差 0.9%–2.4%；稳态并发 2、4 比预测高 21%、45% |
| P6 | 真实 FP8 路径 prefill 更快、解码基本不变 | **被否定** | prefill 快 39%–43%，但并发 1 解码慢 14%（CUTLASS）、65%（Triton） |
| P7 | 用 kernel 对比的参数预测 AIPerf 吞吐，任一格偏差不超过 5% | 未被否定 | 六格偏差都不超过 2.4% |

P6 被否定是这个项目最有用的发现之一：它让我们不再假设「硬件支持就更快」，转而得到负载选择规则。

## kernel 三方对比

三者使用相同的种子和输入，日志级别 INFO，预算 2048，`max-num-seqs=8`，MTP 关闭。前六行是实测，由 `工具/kernel_bench.py compare` 输出；后三行是成本模型换算的稳态预计吞吐，不是 AIPerf 实测。预测 P7 用同样的参数，但按 AIPerf 配对实验的 24 个请求窗口计算，所以数字不同：Marlin / CUTLASS 并发 1 为 26.4 / 25.3，并发 4 为 68.1 / 76.4，并发 8 为 92.0 / 114.6 tok/s。

| 指标 | Marlin | Triton block FP8 | CUTLASS per-channel FP8 |
|---|---:|---:|---:|
| 8192-token prefill 请求耗时 | 3.396 秒 | 1.938 秒 | 2.056 秒 |
| 并发 1 共同解码区间 token 间隔 | 30.83 ms | 50.94 ms | 35.19 ms |
| 并发 4 共同解码区间 token 间隔 | 33.93 ms | 46.71 ms | 38.16 ms |
| 并发 8 共同解码区间 token 间隔 | 35.46 ms | 48.26 ms | 39.52 ms |
| 10625 个文本位置的 top-1 与 Marlin 一致率 | 基准 | 98.36% | 97.34% |
| 同批文本平均 NLL | 0.8807 | 0.8828 | 0.8840 |
| 预计吞吐，并发 1 | 26.4 tok/s | 18.7 tok/s | 25.3 tok/s |
| 预计吞吐，并发 4 | 67.0 tok/s | 62.7 tok/s | 74.9 tok/s |
| 预计吞吐，并发 8 | 90.1 tok/s | 103.1 tok/s | 111.3 tok/s |

Triton 的预计吞吐在所有档位都低于 CUTLASS，只有并发 8 高于 Marlin，因此淘汰。它的日志提示没有对应形状的优化配置，所以这个结果不能推广为 Triton 后端的性能上限。一致率和 NLL 只是低成本的数值检查，不能推出指令遵循质量达标，质量以 IFBench 和小测试集为准。

## CUTLASS 的负载选择规则

CUTLASS 每个输入 token 省约 0.164 ms，每个输出步多花约 4.2 ms，几乎不随批大小变化。所以：

```text
吞吐打平点：输入长度 / 输出长度 ≈ 26 / 并发数
```

官方负载的比值是 16，落在并发 1（平衡点约 26）和并发 2（约 13）之间，所以预计并发 1 输、并发 2 起赢。配对实测并发 1 −3.1%、并发 4 +13.5%、并发 8 +26.6%；四档结果里并发 2 相对官方配置为 {{plan_c2_gain}}。短问题、长回答的负载偏向 Marlin，长文本偏向 CUTLASS。固定开销的机制是根据数据的推断（折算约 10 μs/矩阵），没有 profiler 证据。

## 明确不做的事

- 不改 vLLM 源码，不写自研投机控制器。
- 不量化 `lm_head`，它会改变目标输出，两天内风险太高。
- 不把 prefix caching 当作压测优化：官方输入随机且每档 `cache_salt` 不同，它不起作用。
- 不同时持有两种权重，让 prefill 走 CUTLASS、解码走 Marlin：两份权重放不进这张卡，只作为后续方向。
