# Demo 脚本（3 分钟）

现场真实运行为主，录屏只在现场环境出故障时使用。

**最终配置：** CUTLASS per-channel FP8 + max-num-seqs=8 + 预算 2048

## 上台前

现场使用的配置必须和提交版本一致。不一致要主动说明。

```bash
ssh -N -L 8088:127.0.0.1:8088 <服务器>
```

另开一个终端，字号调大，宽度至少 90 列。先跑一轮预热：首轮含 JIT，会偏慢，随机输入不会污染长文本题的 prefix cache。

```bash
python3 工具/demo.py load --remote "ssh <服务器>"
```

不要提前跑长文本题。第二次运行会命中 prefix cache，耗时明显变短，那不是优化效果。排练过就重启服务（约 1–2 分钟）再预热。

## 流程

```bash
python3 工具/demo.py all --remote "ssh <服务器>"
```

每段结束按回车进入下一段。

| 时间 | 屏幕 | 说什么 |
|---|---:|---|
| 0:00 | 服务、硬件、启动参数、实际 kernel | 这是单张 4090 上正在运行的服务。启动参数和提交版本一致。kernel 名从服务启动日志读取，不是配置文件里写的。 |
| 0:20 | 8 个请求的进度条 | 这是官方的负载形状：输入 8192，输出 512，同时发出。上台前用成本模型算过这一轮的吞吐，屏幕上会看到预计值和实测值。先看首字时间：prefill 要排队，一个接一个做，所以是阶梯状。阶梯的每一级就是一次 prefill 的耗时，这是高并发 TTFT 的主要来源。 |
| 1:05 | 这一轮、成本模型、正式结果 | 这一轮只有 8 个请求，不是正式结果，正式结果是 100 个请求的 115.5 tok/s。它的作用是说明：瓶颈的模型能预测实际跑出来的数字。 |
| 1:20 | 长文本题 | 题目来自小测试集，约 3 万 token 的档案清单，要找到两份档案算差值。第一次运行，要做完整 prefill。 |
| 1:50 | 逻辑题 | 灰色是模型的思考过程，最后一行按规定格式回答，程序判定。 |
| 2:05 | 代码题 | 生成的代码在隔离环境里跑测试，禁止网络和写文件。判定是程序给的，不是人看的。 |
| 2:40 | 优化前后结果表 | 这是正式结果。质量判定：通过。 |

## 出问题时

| 情况 | 处理 |
|---|---|
| 端口转发断了 | 重新运行 `ssh -N -L`，`demo.py` 的报错会提示这一步 |
| 服务挂了 | 重启约 1–2 分钟，时间不够就放录屏，说明原因 |
| 现场网络不通 | 放录屏，说明录制时间和配置 |
| 这一轮明显低于预计 | 如实说，先看 GPU 读数和是否有其他进程占卡，再看是不是预热没做 |
| 某题判定未通过 | 如实说。小测试集基线也有失败题，失败案例写在质量结果里 |
| 某题超过 60 秒 | 脚本自动停止，不判定；继续下一题 |
