## 指标定义

| 指标 | 定义 |
|---|---|
| tok/s | AIPerf 的输出 token 吞吐 |
| TTFT P95 | 全部正式请求首 token 延迟的 P95 |
| 去掉开头后 | 去掉窗口开头同时到达的 c 个请求后的 P95，用来区分开头排队和稳态 |
| TPOT P95 | 每请求 `(端到端 − TTFT) / (输出 token 数 − 1)` 的 P95 |
| 端到端 P95 | 请求总延迟的 P95 |

## 和官方表的差异

自测基线的并发 4 TTFT P95 是 6.09 秒，官方表是 9.39 秒。原因是官方表样本小：把我们的 100 个请求截到官方样本量，前 n 个的 P95 和官方只差 0.9%–2.4%（并发 1、2、4、8），最大值都落在窗口开头。例外是官方并发 2 的 100 请求复测，我们高 7.9%，原因没有查明。

## 测试次数和统计方式

- 每个完整结果跑一次，100 个请求。Marlin 的吞吐可重复性：配对和基线相差不超过 0.18%，并发 8 跨重启相差 0.09%。
- CUTLASS 的配对实验和夜间完整运行是两次独立测量，跨重启波动以这两次为准。
- 所有百分位由赛方解析代码计算，原始逐请求记录见证据索引。

## 异常结果的处理

- **S=128 的 `EngineDeadError`。** 出现在请求结束后服务关停时，已查明，不影响测量，保留在日志里。
- **基线 IFBench 的超时重采。** 14 次 600 秒超时，已完成的题里关联到 3 题。这批结果没有删除，改为保留 89 题、用 3600 秒超时续跑其余 11 题，排除这 3 题后是 77/97。基线因此是混合口径，方案 A 从头使用 3600 秒。
- **逐步日志计时不可用。** `iteration elapsed time` 只包住 `future.result()`，不代表完整步长。发现后改用请求墙钟和流式区间，旧数据留档，不进入结论。
- **Marlin 的功耗上限。** 约 27%–28% 的忙碌秒碰到软件功耗上限，CUTLASS 配对为 0。全程最高 74°C，没有热降频，已如实记录，没有筛除。
